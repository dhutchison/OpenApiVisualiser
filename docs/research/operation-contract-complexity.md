# Research: explainable consumer-facing operation contract complexity

**Issue:** [OpenApiVisualiser #230](https://github.com/dhutchison/OpenApiVisualiser/issues/230)

**Scope:** the effort an API consumer faces when understanding and integrating one declared OpenAPI operation contract, not the provider implementation or undocumented runtime behaviour, following the settled boundary in [Wayfinder map #47](https://github.com/dhutchison/OpenApiVisualiser/issues/47).

**Decision gist for [Wayfinder map #47](https://github.com/dhutchison/OpenApiVisualiser/issues/47):** Replace the naive total with a labelled, multidimensional **contract-burden heuristic** whose explanations come from effective inputs/outputs, schema structure, alternatives and constraints, dependencies, protocol/workflow obligations, and documentation support; calibrate bands empirically and never present the result as measured human effort.

## Executive answer

There is no established primary-source measure that can be transferred intact to this problem. The closest foundations point in the same direction: use a profile, count or flag observable contract properties that plausibly create simultaneously interacting information, keep user/context effects explicit, and validate any aggregation against integration tasks. Cognitive Dimensions is deliberately a broad-brush, multidimensional discussion framework and explicitly avoids an “overall difficulty measure”; its authors call its dimensions vague rather than precise metrics ([Green & Blackwell, *Cognitive Dimensions of Information Artefacts: a Tutorial*, 1998, pp. 4–5, 9](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)). Cognitive-load theory treats experienced complexity as an interaction between information structure and the learner's knowledge, so even a count of interacting elements is an estimate rather than a context-free measurement ([Chen, Paas & Sweller, 2023, §§ “Element Interactivity”, “Measuring Element Interactivity”, “Limitations”](https://doi.org/10.1007/s10648-023-09782-w)). ISO likewise defines usability as an outcome of specified users pursuing specified goals in a specified context, rather than a static property recoverable from an artefact alone ([ISO 9241-11:2018, abstract and clauses 5–7](https://www.iso.org/standard/63500.html)).

The product should therefore report an explainable **estimate of contract burden**, not “cognitive complexity”, “usability”, person-hours, task time, or a scientifically validated effort score. A useful design is six visible dimensions plus a separate confidence/completeness status, consistent with Cognitive Dimensions' profile approach and cognitive-load theory's warning that experienced complexity depends on expertise ([Green & Blackwell, 1998, pp. 5 and 9](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf); [Chen, Paas & Sweller, 2023, §§ “Expertise” and “Limitations”](https://doi.org/10.1007/s10648-023-09782-w)):

1. **Interaction surface** — effective parameters, request alternatives, response cases, headers, and distinct representations.
2. **Data shape** — unique reachable data elements, nesting, collections/maps/tuples, and recursion.
3. **Choice and constraint burden** — unions, conditionals, mutually exclusive alternatives, validation dependencies, and serialization rules.
4. **Dependency and indirection burden** — reference graph breadth/depth, external hops, inherited declarations, and cycles.
5. **Protocol and workflow burden** — security alternatives/combinations, callbacks, links, and operation/server overrides.
6. **Semantic and documentation support** — whether purpose, roles, outcomes, constraints, and examples are made legible; this is a mitigating/support dimension, not permission to erase structural burden.
7. **Confidence/completeness (not aggregated)** — unresolved references, missing schemas or descriptions, unsupported dialect/features, and other reasons the contract may under-describe the real task.

Each dimension should retain its raw observable facts and emit short reasons such as “4 required inputs”, “3 response cases with 2 distinct bodies”, “oneOf with 5 branches”, or “2 external reference hops”. Human-readable overall bands may be derived later by a monotonic, capped aggregation, but weights and thresholds are calibration parameters rather than facts supplied by the literature; the closest quantitative framework was deliberately extensible and evaluated only selected API factors ([Scheller & Kühn, 2015, abstract and §§3–10](https://doi.org/10.1016/j.infsof.2015.01.009)).

## What the current implementation actually measures

At commit `446e6f2`, an operation node starts at zero, calls `calculateComplexity`, and displays the returned integer as an unqualified `Complexity` value in its tooltip ([current service, lines 259–287](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.ts#L259-L287)). The top-level calculation includes a request body and only response keys `200` and `201`; it does not inspect parameters, inherited path-item declarations, other success/error/default responses, security, callbacks, links, server overrides, or operation documentation ([current service, lines 299–315](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.ts#L299-L315)). This is narrower than the OpenAPI Operation Object, which declares parameters, request body, all possible responses, callbacks, security and servers as parts of an operation contract ([OpenAPI Specification 3.1.1, §§4.8.9–4.8.10](https://spec.openapis.org/oas/v3.1.1.html#operation-object)).

The recursive routine initializes each defined object to one, adds counts for `items`, `allOf`, `anyOf`, `oneOf`, references, and immediate property names, and subtracts the traversal of `not` ([current service, lines 318–359](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.ts#L318-L359)). Subtraction for `not` has no defensible semantic interpretation: in JSON Schema, `not` inverts a subschema's validation result and is an applicator/constraint, not removal of information a consumer must understand ([JSON Schema Core 2020-12, §10.2.1.4](https://json-schema.org/draft/2020-12/json-schema-core.html#section-10.2.1.4)). Arrays of subschemas are also passed as ordinary objects, so the intended composition traversal does not iterate their branches ([current service, lines 343–357](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.ts#L343-L357)).

More fundamentally, request and response objects are recognized by the presence of `content`, after which the routine iterates the top-level object's fields rather than the media-type entries inside `content`; the content map itself matches no type guard, so ordinary body schemas are not reached through this path ([current service traversal, lines 328–340](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.ts#L328-L340); [current type guards, lines 420–469](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.ts#L420-L469)). Repeated and recursive `$ref` values have no visited set in this calculation, although a different schema-tree path now has cycle protection; a recursive contract can therefore recurse without a meaningful bound in the score path ([current service, lines 337–370](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.ts#L337-L370)).

The only direct complexity expectation in the service tests is a tooltip value of `1` for a `200` response containing only a description; it verifies newline rendering, not a complexity model, schema traversal, breadth of contract coverage, monotonicity, or cycle handling ([current test, lines 62–91](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.spec.ts#L62-L91)). The existing integer is consequently best treated as historical implementation behaviour, not as evidence that recursive node counting measures consumer effort.

## Useful informing models and evidence

### 1. Cognitive Dimensions of Notations: use the vocabulary and profile, not a borrowed score

Green and Petre introduced the framework in peer-reviewed form as a broad-brush vocabulary for cognitively relevant aspects of interactive devices and non-interactive notations ([Green & Petre, “Usability Analysis of Visual Programming Environments: A ‘Cognitive Dimensions’ Framework”, *Journal of Visual Languages & Computing* 7(2), 1996, pp. 131–174](https://doi.org/10.1006/jvlc.1996.0009)). Green and Blackwell's later tutorial describes Cognitive Dimensions as checklist-like “discussion tools” for evaluating information artefacts, including static notations, and says that a profile across dimensions should replace a single overall difficulty judgement ([Green & Blackwell, 1998, pp. 4–5, 9–10](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)). This fits an OpenAPI document as a static information artefact and supports a multidimensional explanation, but it does not supply numeric weights or thresholds.

Three requested dimensions have precise relevance:

- **Hidden dependencies** are important links between entities that are not visible; long, branching dependency trails make search onerous and slow information finding ([Green & Blackwell, 1998, pp. 10, 16–19](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)). This supports exposing reference hops, inheritance/override relationships, cross-operation links, and callback dependencies. It does not prove that each `$ref` adds one equal unit of effort.
- **Role expressiveness** asks whether the purpose of a component, action, or symbol is readily inferred and whether relationships between parts can be picked out when reading ([Green & Blackwell, 1998, pp. 10, 40](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)). This supports a documentation/semantic-support dimension for names, summaries, descriptions, examples and explicit relationships. It does not justify scoring prose by length.
- **Viscosity** is resistance to change: repetition viscosity requires many actions for one conceptual change, while knock-on viscosity requires follow-up actions to restore consistency ([Green & Blackwell, 1998, pp. 11–13](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)). A single OpenAPI snapshot cannot reveal the actions needed to update a consumer integration, so viscosity should not contribute to the base understand-and-integrate score. It can inform a future version-diff/change-impact profile if the product explicitly models consumer adaptation work.

Microsoft adapted Cognitive Dimensions to API evaluation and retained API viscosity and role expressiveness alongside abstraction level, consistency, penetrability, domain correspondence and other dimensions; its evaluation method still used usability studies and persona-specific profiles rather than a universal static score ([Clarke, “Describing and Measuring API Usability with the Cognitive Dimensions”, 2005, pp. 1–2](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/workshop2005/Clarke_position_paper.pdf)). That first-party experience strengthens the choice of an API-specific profile while warning against presenting one persona-independent number as “API usability”.

### 2. Cognitive load and interacting information elements: count relations, not just nodes

Cognitive-load theory distinguishes the number of things present from the number that must be processed together: non-interacting elements can be learned separately, whereas interacting elements must be handled simultaneously to understand the material ([Chen, Paas & Sweller, 2023, §§ “Element Interactivity” and “The Distinction Between Element Interactivity and Task Difficulty”](https://doi.org/10.1007/s10648-023-09782-w)). This is the strongest theoretical reason to separate flat surface size from branch/constraint/dependency structure. Ten independent optional fields and five mutually constrained fields should not be assumed to impose the same kind of burden.

The same paper also makes two limits unavoidable: what counts as one element changes with prior knowledge, and element-interactivity counts are estimates whose accuracy depends on knowledge of the learner ([Chen, Paas & Sweller, 2023, §§ “Expertise, Strategy Use, and Element Interactivity”, “Measuring Element Interactivity”, and “Limitations”](https://doi.org/10.1007/s10648-023-09782-w)). Contract-visible counts can therefore be stable properties of the document, but translating them into experienced effort requires an explicit reference user and empirical calibration.

### 3. API Concepts Framework: factor user actions, measurable properties and learning effects

Scheller and Kühn's API Concepts Framework decomposes API use into concepts representing user actions, measurable properties influencing those concepts, and learning effects representing experience; the authors evaluated selected properties with usability studies and describe their result as extensible rather than complete ([Scheller & Kühn, “Automated measurement of API usability: The API Concepts Framework”, *Information and Software Technology* 61 (2015), pp. 145–162, abstract and §§3–10](https://doi.org/10.1016/j.infsof.2015.01.009)). The transferable lesson is architectural: preserve factor-level observations and distinguish first-use burden from learning effects. Its studied object-oriented API concepts and fitted values should not be copied as OpenAPI weights without a new validation study.

### 4. Direct API-usability and Web-API understandability evidence

Several primary empirical studies support specific dimensions but not a complete operation metric:

- A mixed-method field study of more than 440 professional developers found severe API-learning obstacles in documentation and learning resources, and identified documentation of intent, code examples, matching APIs to scenarios, penetrability, and format/presentation as important documentation factors ([Robillard & DeLine, “A field study of API learning obstacles”, *Empirical Software Engineering* 16 (2011), pp. 703–732](https://www.microsoft.com/en-us/research/publication/field-study-api-learning-obstacles/)). This directly supports documentation and example coverage as observable support signals, while also showing why in-contract text cannot represent all available learning resources.
- A study of 25 programmers using a persistence API found difficulties with feature names and discovering relations between API types, observed an impact from flexibility, and confirmed the importance of accurate documentation ([Piccioni, Furia & Meyer, “An Empirical Study of API Usability”, ESEM 2013, pp. 5–14](https://doi.org/10.1109/ESEM.2013.14)). This supports semantic legibility, dependency visibility and alternative/choice burden, but the sample and object-oriented setting do not validate a particular OpenAPI formula.
- In experiments with alternative object-oriented APIs, programmers were 2–11 times faster at combining objects when the class they started from visibly referenced the other needed class ([Stylos & Myers, “The Implications of Method Placement on API Learnability”, FSE 2008, pp. 105–112](https://www.cs.cmu.edu/~NatProg/papers/FSE2008-p105-stylos.pdf)). This is strong evidence that discoverable relationships matter, but method placement is not equivalent to `$ref` count; it informs the dependency dimension rather than setting its weight.
- A controlled Web experiment with 105 participants tested 12 RESTful API design rules using paired API descriptions; 11 violations reduced comprehension performance and 9 were rated harder, with effects varying substantially by rule ([Bogner, Kotstein & Pfaff, “Do RESTful API design rules have an impact on the understandability of Web APIs?”, *Empirical Software Engineering* 28, article 132 (2023), §§3–4 and 6](https://doi.org/10.1007/s10664-023-10367-y)). This directly supports semantic-convention/anomaly flags for URI, HTTP method and status-code use, but it argues against collapsing all violations into an equal generic count.

### 5. OpenAPI and JSON Schema: authoritative inventory, not human-effort validation

OpenAPI defines the contract-visible surface that the heuristic may inspect. An effective operation includes path-item parameters plus operation-level overrides, a request body, the list of possible responses, callbacks, security alternatives, and servers ([OpenAPI Specification 3.1.1, §§4.8.9–4.8.10](https://spec.openapis.org/oas/v3.1.1.html#operation-object)). Parameter location, requiredness, schema/content and serialization `style`/`explode` change what a consumer must send ([OpenAPI Specification 3.1.1, §4.8.12](https://spec.openapis.org/oas/v3.1.1.html#parameter-object)). Request and response content maps express representation choices, while responses may use individual status codes, ranges and `default`, and response objects may add headers, links and content ([OpenAPI Specification 3.1.1, §§4.8.13–4.8.17](https://spec.openapis.org/oas/v3.1.1.html#responses-object)). Security arrays express OR alternatives while multiple schemes within one requirement express AND combinations ([OpenAPI Specification 3.1.1, §4.8.30](https://spec.openapis.org/oas/v3.1.1.html#security-requirement-object)). Callbacks describe provider-initiated requests and their expected responses, extending the consumer's workflow beyond one request/response pair ([OpenAPI Specification 3.1.1, §4.8.18](https://spec.openapis.org/oas/v3.1.1.html#callback-object)).

OAS 3.1 Schema Objects inherit JSON Schema 2020-12 semantics ([OpenAPI Specification 3.1.1, §4.8.24](https://spec.openapis.org/oas/v3.1.1.html#schema-object)). JSON Schema applicators such as `allOf`, `anyOf`, `oneOf`, `not`, `if`/`then`/`else`, `dependentSchemas`, `properties` and `items` determine which subschemas apply, while validation keywords assert requirements such as `required`, numeric/string/array limits and `dependentRequired` ([JSON Schema Core 2020-12, §§10–11](https://json-schema.org/draft/2020-12/json-schema-core.html#section-10); [JSON Schema Validation 2020-12, §§6–9](https://json-schema.org/draft/2020-12/json-schema-validation.html#section-6)). These specifications justify what must be resolved and explained; they do not claim that keyword or property counts predict human effort.

Depth cut-offs and weights require calibration. |
| Choice and constraint burden | `oneOf`/`anyOf` branches, conditionals, dependent requirements/schemas, `not`, overlapping alternatives, enum/const choices when selection affects behaviour, media types, parameter serialization, response and security alternatives | Interacting alternatives and conditional obligations are closer to element interactivity than raw node count ([Chen, Paas & Sweller, 2023, §§ “Element Interactivity” and “Task Difficulty”](https://doi.org/10.1007/s10648-023-09782-w)). | Semantic and documentation support | Presence and task relevance of summary/description, parameter/property/response descriptions, examples, external documentation links, meaningful identifiers, explicit discriminator mapping, conventional HTTP semantics | Role expressiveness concerns whether purpose and relationships are readily inferred ([Green & Blackwell, 1998, p. 40](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)); direct API studies support intent documentation, examples, names, relationship discovery and conventional Web-API semantics ([Robillard & DeLine, 2011](https://www.microsoft.com/en-us/research/publication/field-study-api-learning-obstacles/); [Piccioni, Furia & Meyer, 2013](https://doi.org/10.1109/ESEM.2013.14); [Bogner, Kotstein & Pfaff, 2023](https://doi.org/10.1007/s10664-023-10367-y)). | **Direct relevance, difficult automation.** Presence/absence and lintable convention violations are proxies; prose length and field presence do not establish accuracy or usefulness. |

### Important counting rules

- Resolve the **effective operation** before measuring: merge inherited path-item parameters, apply operation overrides, and resolve effective global/operation security because OAS assigns these declarations semantic effect ([OAS 3.1.1, §§4.8.9–4.8.10 and 4.8.30](https://spec.openapis.org/oas/v3.1.1.html#operation-object)).
- Traverse a graph with identity and cycle detection. Count a shared schema concept once in structural size for a given request/response role, then report reuse, hop depth, externality and recursion separately; this avoids both infinite recursion and treating repeated notation as repeated knowledge while retaining the hidden-dependency signal ([Green & Blackwell, 1998, pp. 16–19](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)).
- Separate **alternatives** from duplicate representations. Three media types with the same reachable shape create a representation choice but not three independently novel data models; OAS defines media-type keys as request/response alternatives ([OAS 3.1.1, §§4.8.13–4.8.17](https://spec.openapis.org/oas/v3.1.1.html#media-type-object)).
- Preserve request and response roles. `readOnly` and `writeOnly` affect whether requiredness applies to responses or requests, so one undifferentiated property count misstates the effective contract ([OAS 3.1.1, §4.8.24.3.2](https://spec.openapis.org/oas/v3.1.1.html#fixed-fields-20)).
- Treat recursion as a structural characteristic, not infinite size, and surface the traversal limit. OAS explicitly warns that reference cycles may cause unbounded resource consumption during processing ([OAS 3.1.1, §5.5](https://spec.openapis.org/oas/v3.1.1.html#handling-reference-cycles)).
- Do not reward omission. A response with no declared schema is less knowable, not necessarily easier; put missing information in confidence/completeness and keep it out of the structural denominator ([OAS 3.1.1, §§2 and 4.8.17](https://spec.openapis.org/oas/v3.1.1.html#response-object)).

## Concrete product recommendation

### Recommended output model

For each operation, produce a versioned `Contract burden profile` consisting of the six dimensions above. Each dimension should have:

- normalized raw facts;
- an ordinal contribution (for example, low/moderate/high/very high);
- one or more plain-language reasons;
- a support label: `observed`, `proxy`, or `unknown/incomplete`.

This structure follows Cognitive Dimensions' profile model and avoids the framework's explicitly rejected overall-difficulty framing ([Green & Blackwell, 1998, pp. 5 and 9](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)). It also resembles the API Concepts Framework's separation of user-action concepts, measurable properties and learning effects without transferring its API-specific fitted values ([Scheller & Kühn, 2015, §§3 and 6–9](https://doi.org/10.1016/j.infsof.2015.01.009)).

An overall display band can be useful for scanning, but it should be derived from the dimension contributions with a transparent monotonic rule and never be the only output. Before empirical calibration, use equal-status dimensions and conservative ordinal thresholds chosen from a published representative OpenAPI corpus; cap each dimension so one giant flat DTO cannot drown out all interaction structure. After calibration, fit or adjust thresholds against task outcomes and publish a model version, target user, corpus, and changed weights. These are product-method recommendations, not values established by the cited research.

A compact explanation should therefore read more like:

> **High contract burden** — 7 required inputs; 4 distinct response cases; 3 schema alternatives with conditional requirements; 2 external reference hops; OAuth2 plus API-key combination; request examples missing. Confidence: reduced by one unresolved reference.

That wording remains auditable to the document and separates the estimate from its evidence. “High cognitive complexity: 27” would incorrectly imply a validated psychometric scale, contrary to Cognitive Dimensions' discussion-tool status and cognitive-load theory's expertise dependence ([Green & Blackwell, 1998, pp. 4–5](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf); [Chen, Paas & Sweller, 2023, §§ “Expertise” and “Limitations”](https://doi.org/10.1007/s10648-023-09782-w)).

### Calibration and validation

Calibration should define concrete consumer tasks (identify required inputs, construct a valid request, handle success and failure, configure authorization, and implement any callback), target populations, and contexts. That is required because usability is an outcome of specified users, goals and context ([ISO 9241-11:2018, clauses 3 and 5–7](https://www.iso.org/standard/63500.html)). For stratified real and synthetic operations, collect task completion, errors, time, and comprehension accuracy; use those observations to test monotonicity and threshold placement rather than claiming that raw counts are effort units. Direct API studies have successfully used task performance, comprehension questions, time and perceived difficulty, providing relevant methodological precedents ([Piccioni, Furia & Meyer, 2013](https://doi.org/10.1109/ESEM.2013.14); [Bogner, Kotstein & Pfaff, 2023, §3](https://doi.org/10.1007/s10664-023-10367-y)).

NASA-TLX may supplement such a study as a post-task subjective workload outcome. It combines ratings of mental demand, physical demand, temporal demand, performance, effort and frustration, and its own authors describe subjective workload as the intersection of objective task demands and the individual's response ([Hart & Staveland, “Development of NASA-TLX”, in *Human Mental Workload*, 1988, pp. 139–183](https://human-factors.arc.nasa.gov/groups/TLX/downloads/Hart_Staveland_ORIGINAL_1.pdf); [NASA's official TLX page](https://www.nasa.gov/human-systems-integration-division/nasa-task-load-index-tlx/)). It is not a formula that can score an OpenAPI document without people performing a task.

### Migration interpretation

The present value should not be normalized into the new bands because it neither covers the effective operation nor reliably reaches ordinary body schemas ([current service, lines 299–359](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.ts#L299-L359)). Treat it only as the historical UI field to be conceptually replaced. Existing tooltip tests establish rendering behaviour, not numerical compatibility ([current test, lines 62–91](https://github.com/dhutchison/OpenApiVisualiser/blob/446e6f2af3062a4be189225d86fd7af1aeecf29d/src/app/services/openapi-treenode-converter.service.spec.ts#L62-L91)).

## Limitations and non-claims

- The heuristic estimates **declared contract burden for a reference consumer**. It cannot measure an individual's cognitive load, usability, integration time or productivity because expertise, goals, tools and context change experienced difficulty ([Chen, Paas & Sweller, 2023, §§ “Expertise” and “Limitations”](https://doi.org/10.1007/s10648-023-09782-w); [ISO 9241-11:2018](https://www.iso.org/standard/63500.html)).
- OpenAPI visibility is a hard boundary. Credential issuance, support quality, SDK quality, undocumented business rules, service reliability, latency and runtime data-dependent behaviour are not inferable from the operation contract; OAS describes the interface surface, not provider internals or all operating context ([OAS 3.1.1, §§2–3](https://spec.openapis.org/oas/v3.1.1.html#introduction)).
- Documentation presence is not documentation correctness. Empirical evidence establishes the importance of intent, examples and accuracy, but a static checker can only observe incomplete proxies without semantic/user evaluation ([Robillard & DeLine, 2011](https://www.microsoft.com/en-us/research/publication/field-study-api-learning-obstacles/); [Piccioni, Furia & Meyer, 2013](https://doi.org/10.1109/ESEM.2013.14)).
- Larger is not always harder, and smaller is not always easier. Cognitive-load theory distinguishes many independent elements from fewer interacting elements, while missing declarations can create uncertainty rather than low burden ([Chen, Paas & Sweller, 2023, § “The Distinction Between Element Interactivity and Task Difficulty”](https://doi.org/10.1007/s10648-023-09782-w); [OAS 3.1.1, §3.9](https://spec.openapis.org/oas/v3.1.1.html#undefined-and-implementation-defined-behavior)).
- A band is a product decision calibrated for comparison and navigation, not a natural unit. Model versioning, a disclosed reference population, representative fixtures and regression checks are necessary to keep it stable; the informing models provide a broad profile or expertise-dependent estimates rather than OpenAPI-specific cut-points ([Green & Blackwell, 1998, pp. 4–5 and 43](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf); [Chen, Paas & Sweller, 2023, §§ “Measuring Element Interactivity” and “Limitations”](https://doi.org/10.1007/s10648-023-09782-w)).
- The profile is not a normative grade of API quality. Cognitive Dimensions says dimensions are not intrinsically good or bad and suitability depends on the activity; flexibility, abstraction and indirection can trade benefits against costs ([Green & Blackwell, 1998, pp. 5, 9 and 41–43](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)).

## Rejected near-neighbours

These models are established, but their measured object differs from consumer-facing operation-contract burden.

| Model or measure | What its primary source measures | Decision for this product |
|---|---|---|
| **Halstead software science** | Halstead derives program vocabulary, volume, difficulty and effort from distinct and total **operators and operands in program text** ([Halstead, *Elements of Software Science*, Elsevier, 1977, ISBN 9780444002150](https://books.google.com/books/about/Elements_of_Software_Science.html?id=rRIpAQAAMAAJ)). | **Reject as a formula.** An OpenAPI contract is not source-code operator/operand vocabulary, and renaming JSON/YAML tokens as operands would not validate the derived “effort”. The useful residue is only the general discipline of declaring primitive counts before deriving a score. |
| **McCabe cyclomatic complexity** | McCabe's graph-theoretic measure controls the number of independent paths through a **program's control-flow graph**, with (V(G)=e-n+2p) ([McCabe, “A Complexity Measure”, *IEEE Transactions on Software Engineering* SE-2(4), 1976, pp. 308–320](https://doi.org/10.1109/TSE.1976.233837)). | **Reject.** Response codes, `oneOf` branches and callbacks are contractual alternatives, not executable provider control-flow paths; constructing a fake CFG changes the measured concept. |
| **Sonar Cognitive Complexity** | Sonar defines a source-code metric for how hard a method's **control flow** is to understand, incrementing for breaks in linear flow and nesting, with language-specific rules ([SonarSource, *Cognitive Complexity* white-paper landing page](https://www.sonarsource.com/resources/cognitive-complexity/); [SonarQube metric definition](https://docs.sonarsource.com/sonarqube-server/user-guide/code-metrics/metrics-definition)). | **Reject despite the name.** It measures source maintainability/understandability, not a consumer's declarative HTTP contract. Its explain-at-each-contributor presentation is worth emulating, not its scoring rules. |
| **Function points / COSMIC** | Albrecht and Gaffney frame software function and source lines as predictors of programming-system size and **development effort** ([Albrecht & Gaffney, “Software Function, Source Lines of Code, and Development Effort Prediction”, *IEEE TSE* SE-9(6), 1983, pp. 639–648](https://doi.org/10.1109/TSE.1983.235271)). COSMIC standardizes **functional size** by counting data movements in functional user requirements ([ISO/IEC 19761:2011](https://www.iso.org/standard/54849.html); [COSMIC Measurement Manual v5.0, Part 1](https://cosmic-sizing.org/wp-content/uploads/2020/06/Part-1-MM-Principles-Definitions-Rules-v5.0-Feb-2021.pdf)). | **Reject as consumer effort.** These can size delivered functionality or support producer estimation; an operation with one functional process can still be difficult to understand, and many data movements do not establish integration burden. |
| **Maintainability Index** | Oman and Hagemeister's measure is explicitly an index for assessing a **software system's maintainability**, built from source-code measurements ([Oman & Hagemeister, “Metrics for assessing a software system's maintainability”, ICSM 1992, pp. 337–344](https://doi.org/10.1109/ICSM.1992.242525)). | **Reject.** It targets maintenance of the provider/source artefact, not comprehension of a consumer-visible operation contract; its constituent code metrics inherit the same mismatch. |
| **Asymptotic/runtime complexity** | Algorithm analysis studies resource growth such as worst-case running time as input size grows ([Cormen, Leiserson, Rivest & Stein, *Introduction to Algorithms*, 4th ed., MIT Press, 2022](https://mitpress.mit.edu/9780262046305/introduction-to-algorithms/); [MIT 6.046J syllabus](https://www.ocw.mit.edu/courses/6-046j-design-and-analysis-of-algorithms-spring-2015/pages/syllabus/)). | **Reject.** Runtime time/space behaviour is normally absent from an OpenAPI operation description and is explicitly outside consumer contract understanding. Array schemas describe allowed shapes, not asymptotic execution cost. |
| **NASA-TLX** | NASA-TLX is a multidimensional **subjective workload assessment** completed by operators in a task context, using six rated subscales ([NASA official TLX documentation](https://www.nasa.gov/human-systems-integration-division/nasa-task-load-index-tlx/); [Hart & Staveland, 1988, pp. 139–183](https://human-factors.arc.nasa.gov/groups/TLX/downloads/Hart_Staveland_ORIGINAL_1.pdf)). | **Reject as a static contract score; retain for validation.** It requires participant judgements after or during tasks and cannot be inferred from schema counts. |
